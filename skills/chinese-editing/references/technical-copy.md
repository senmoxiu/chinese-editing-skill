# 技术与界面文案

用于操作说明、API 文档、状态、错误提示、按钮和空状态。先从提供的接口、代码或产品要求确认行为；短按钮任务无需展开成完整技术报告。

## 技术说明

说明读者要完成的动作、必要前提及可观察结果。把关键条件放到相关动作之前，分清用户操作与系统自动行为。需要严格先后执行的动作才编号；不要为缩短句子拆散条件和否定关系。

技术参数尽可能说明类型、单位、可选值和缺省行为，但这些信息必须来自实际定义。`timeout` 没有资料时不能补上秒／毫秒，更不能猜默认值。缺口可以另列，不把“待确认”作为正式 API 值写入示例。

保留命令、参数与返回值的准确字面量。排查说明区分观察、原因假设与证据支持的结论；不凭文案任务增加重启、删数据或修改安全配置等操作。

## 状态要对应真实阶段

不要把英文词逐项固定翻译成一个中文词。先区分请求接收、后台执行、业务结果和界面呈现。例如接口已接收任务但仍在排队，应说明“已提交，等待处理”，不能写成“处理完成”。只有接口或产品提供了完成时限时，才展示预计时间。

认证问题、权限不足、记录不存在和请求格式错误应按已知原因区分。信息不足时用可证实的失败描述，不猜服务器原因，也不自动把所有认证错误都解释为“请重新登录”。

## 按钮与确认

按钮表达当前动作，必要时写出对象，例如“导出报告”。“保存并提交”只有确实同时发生两种行为时才使用。空间有限时可把条件放在附近帮助文本中。

涉及删除或覆盖的文案必须与实际的可恢复性相符。未知恢复能力不能写“可在回收站恢复”，也不能擅自宣称“永久删除”。确认文本可说明对象和后果，按钮保持简短。

## 错误与空状态

错误提示优先说明失败的动作、已知影响与可行的下一步。不责怪用户，不让用户执行产品没有提供的入口。不知道文件是否保存成功时，不能承诺“内容已安全保存”。

空状态至少区分：尚未创建、筛选无结果、没有访问权限、加载失败。没有搜索结果可建议调整已有筛选条件；加载失败不应显示成“暂无数据”。

文案顺序与长度服从实际界面。屏幕阅读器标签可以补充图标按钮的含义；不要依靠颜色、表情或“点击右边”作为唯一定位信息。未检查页面时，不宣称可访问性或布局已经验证。

## 本地化资源

只编辑已确定属于用户可见文案的值，保留键、枚举、插值、转义、标记及复数分支。修改前后比对占位符；若模板含复杂语法，使用项目已有解析或编译检查。

示例：`{"retry":"请等待{seconds}秒后重试"}` 可把值改为 `请等待 {seconds} 秒后重试`；`retry` 与 `{seconds}` 不变。这个操作需要用户已要求修改界面文案，不属于普通正文格式化。

## 缺失信息的处理

能写出保守且准确的文案时先交付。多个分支会实质改变提示或用户操作时，列出依赖条件，或询问最少的关键事实。不要为了让稿件显得完整而补造业务规则。
